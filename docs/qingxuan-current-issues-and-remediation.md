### 行为与兼容性

- 待审批默认有效期为 15 分钟，从人工审批请求创建时开始；Web 展示到期时间。注册表的 `approvalTimeoutMs` 构造参数可调整有效期，目前没有新增环境变量或管理页开关。到期后需重新发起工具调用和审批。
- `ToolApprovalRegistry.decide()` 现在返回 `Promise<boolean>`；Web 路由已改为等待结果。外部集成若直接调用该方法，也必须 `await`，不能将 Promise 对象当作批准成功。
- Web 审批 API 新增 `expiresAt` 和 `payloadHash`。摘要用于关联本次工具参数与审计记录，不是签名或文件完整性证明；审计事件不新增原始参数副本。
- `tool_approval_decided` 表示操作员决定，不保证工具已经执行。随后取消、过期或参数变化仍可阻断工具，执行结果须结合工具事件判断。
- 未提供 `executionLogProvider` 的独立注册表仍保留无持久审计用法；已配置提供器返回空值不再被当作“关闭审计”。生产 Web 实例使用已配置提供器的严格路径。
- 原有任务并发、扫描参数、工具集合、模型评估正常路径和显式关闭审批的语义均未改变。只读快速路径不新增模型请求或持久化写入；人工批准路径增加必要的审计等待，较长参数和裁判故障可能增加人工等待。**未运行渗透效果或吞吐基准，不能承诺性能零变化。**

## 一、总体判断

青玄已经有容器隔离、网络范围控制、工具审批、任务停止与执行日志，不能简单评价为“完全没有安全机制”。但这些机制尚不足以支持“可以无人值守地测试生产系统，而且保证无损”的承诺。

主要差距不是缺一句安全提示词，而是：

1. 部分调用是否执行，仍主要依赖模型判断，且存在特定异常放行。
2. 人工或模型看到的审批信息可能少于实际执行内容。
3. 网络地址范围、业务操作范围与生产影响边界没有形成完整对应关系。
4. 任务并发、容器资源限制不能替代目标级流量和操作预算。
5. 停止、审计、凭据和外部工具需要形成覆盖完整执行链的保障。

这些判断的代码依据见下文。推荐目标是：**在已经验证的可信执行基础成立时，即使模型提出危险动作，也无法超越明确的执行权限；对权限范围内的残余风险，能够限制影响、及时停止和追踪恢复。** 这仍不是零风险保证。

- **P0：生产开放前处理。** 适用于拟开放的执行能力及其控制路径，不表示已确认发生最高等级事故。
- **P1：首轮系统化加固。** 若目标环境涉及敏感凭据、数据或高影响操作，相应项目应提升为 P0。
- **P2：扩大覆盖与持续优化。** 不包括可以延期的核心安全验收；核心控制必须先验证再上线。

## 四、逐项问题与解决方法

### QX-S01：自动审批的异常放行

**现状与依据**

默认审批模式为 `auto`。在进入 LLM 裁判的调用路径中，`judge.assess` 抛出 `LlmJudgeUnavailableError` 后，如果工具不匹配静态危险工具列表，扩展直接返回。这表示这次调用不再等待人工审批。

依据：[dangerous-tool-policy.ts:19](../src/approval/dangerous-tool-policy.ts#L19)、[tool-approval-extension.ts:64](../src/approval/tool-approval-extension.ts#L64)。注意：没有裁判对象、裁判评估失败、任意其他异常不是同一种分支，不能统称“所有错误都会放行”。

**风险**

新工具或插件可能具备网络或写入能力，却没有被静态列表识别。裁判不可用时，恰好缺少足够判断的信息，却减少了审批限制。

**解决方案**

1. 将未知工具和无法完成评估的动作默认拒绝，或转入独立人工审批；没有审批渠道时拒绝。
2. 为工具登记结构化风险元数据，不只根据名称判断读写和网络行为。
3. 明确三类动作：自动允许、必须审批、始终禁止；LLM 不得覆盖“始终禁止”。
4. 裁判可提供解释或建议提高风险级别，但不得单独扩大动作能力和授权范围。
5. 对 `strict` 保留“裁判仅生成说明、不能取消审批”的性质。

**最小验收**：裁判异常、无响应和未知工具场景下，执行器调用计数保持为零；已确认的低影响能力仍能按政策正常运行。

### QX-S02：审批输入截断

**现状与依据**

裁判输入参数最多保留前 4,000 字符，Web 审批参数最多展示前 8,000 字符，CLI 展示也限制为 4,000 字符。

依据：[llm-risk-judge.ts:186](../src/approval/llm-risk-judge.ts#L186)、[tool-approval-registry.ts:183](../src/approval/tool-approval-registry.ts#L183)、[tool-approval-extension.ts:186](../src/approval/tool-approval-extension.ts#L186)。

**风险**

审阅前缀后批准完整执行，存在审阅对象与执行对象不一致的问题。这里确认的是信息不完整，不是已经证明某个载荷可成功绕过。

**解决方案**

1. 显示摘要与后台授权对象分开；完整规范化参数保存为不可变审批附件。
2. 参数超过评估能力时，拒绝自动批准，不能仅截断后继续问裁判。
3. 人工审批页面支持查看完整参数及引用脚本，明确提示摘要不完整。
4. 对任意可执行脚本，不把“分块都评过”当成组合语义已安全；不支持的执行形式转人工或隔离环境。
5. 保存哈希与审阅记录时保护原始敏感内容，不把完整密钥重新泄露给无权限用户。

**最小验收**：超长内容不会基于前缀自动批准；UI 折叠不改变后台授权内容；实际执行与审批快照一致。

### QX-S03：审批没有完整绑定执行时内容

**现状与依据**

当前随机 ID 和 Promise 已绑定具体待调用对象，决定后 ID 被移除，这是有效基础。但队列设计没有超时，未见对引用脚本内容、工具版本、scope 版本及执行前文件变化的完整绑定。

依据：[tool-approval-registry.ts:7](../src/approval/tool-approval-registry.ts#L7)、[同文件:74](../src/approval/tool-approval-registry.ts#L74)、[同文件:121](../src/approval/tool-approval-registry.ts#L121)。

**风险**

批准执行某个文件，不一定等于批准文件后来变化后的内容；较早的批准也可能在任务范围、预算或目标状态发生变化后失去原来的适用条件。

**解决方案**

建议绑定 `runId`、`taskId`、工具 ID、规范参数摘要、实际脚本/载荷哈希、工具/镜像版本、目标、策略版本、预算、有效期和允许次数。执行前重新校验，过期或变更则重新审批。

同进程实现可采用不可变快照和原子消费，不必一开始引入复杂签名基础设施；跨进程或外部执行器再采用经过认证、不可转用的一次性授权凭证。不能仅“检查文件哈希后按原路径执行”，还应执行已经固定的内容，避免检查与使用之间再次变化。

**最小验收**：修改引用文件、变更策略、审批过期或重复消费后均不能执行；取消任务应使未使用授权失效。

### QX-S04：范围语义与执行粒度不一致

**现状与依据**

TypeScript 对普通域名允许其子域；DNS 侧普通域名按精确匹配处理。网关把匹配域名的 DNS IPv4 答案加入允许集合，放行规则本身不表达目标端口、站点、路径、租户或操作。

依据：[scope.ts:25](../src/scope.ts#L25)、[scope_dns.py:43](../network-image/scope_dns.py#L43)、[同文件:62](../network-image/scope_dns.py#L62)、[index_server.py:901](../network-image/index_server.py#L901)。CTF 的全 IPv4 默认范围见 [scope.ts:21](../src/scope.ts#L21)。

**风险**

同一个 IP 可能承载不止一个授权服务。不同层的域名匹配不一致，也可能表现为误阻断，而不是必然扩大权限。当前机制不能据此承诺 URL 或租户级隔离。

**解决方案**

1. 统一规则：精确域名与显式子域通配符分开，并跨语言共用测试用例。
2. 区分“允许正常访问”“允许主动测试”“禁止访问”；第三方依赖不应因页面引用就成为测试目标。
3. 对每次连接、DNS 变化和重定向逐次验证；使用已验证地址建立连接。
4. Web 出口需要能核验实际请求的协议适配器；加密流量无法仅靠目的 IP 过滤实现路径授权。不具备所需校验能力时拒绝该模式。
5. 其他协议按协议声明能力；不能假定一个 HTTP 代理覆盖所有流量。
6. 阻止绕开控制出口的直接连接，并明确 IPv6、UDP、浏览器子资源及代理的覆盖状态。
7. CTF 全范围配置只限隔离环境，不得自动继承到生产任务。

**最小验收**：相同 scope 在控制面和 DNS 侧得到一致结果；共享 IP 的非授权服务、跨域跳转和未覆盖出口被拒绝或明确禁用。目标端 SSRF 等二次连接不一定经过本地网关，必须另行限制，不能给出本地出口包办的保证。

### QX-S05：没有统一的目标压力与操作预算

**现状与依据**

控制器有任务并发限制，容器有 CPU、内存和 PID 限制，但一个工具内部仍可能产生大量请求。本次检查控制器、执行器、审批与网关，未找到完整的跨工具目标预算实现。模型供应商的限流错误处理不能充当目标限流。

依据：[controller.ts:243](../src/controller.ts#L243)、[同文件:2415](../src/controller.ts#L2415)、[executor-sandbox-docker.ts:153](../src/executor-sandbox-docker.ts#L153)。

**解决方案**

建立任务、目标服务、账户、网段和整个测试活动的分层预算，至少包含连接数、速率、突发、总请求、认证失败次数与写入上限。由独立控制点聚合计数，不能由各 Agent 自报。

对多任务并发做原子扣减；资源预留失败则不执行。重试、恢复任务和新建子任务不得重置业务预算。无法解析账户失败或写入语义的协议，应使用固定能力适配器或禁止对应操作。具体阈值由业务容量和授权规则决定，不给所有目标套同一默认 RPS。

**最小验收**：多个任务同时请求同一目标时，实际总流量符合预算；连续失败认证达到阈值后停止，不能换工具继续累积。

### QX-S06：缺少目标业务健康闭环

**现状与依据**

本次所读 [控制器](../src/controller.ts)、[网关](../network-image/index_server.py) 与 [执行器](../src/executor-sandbox-docker.ts) 中，未找到统一的“目标基线、业务退化检测、暂停、恢复授权”闭环。工具返回错误或容器存活并不代表目标业务正常。

**解决方案**

在批准的窗口内采集低开销目标基线，接入业务方认可的延迟、错误率、数据库连接池、账户锁定等指标。建立正常、降速、暂停、人工确认恢复的状态机。关键健康数据不可用时，生产高影响动作默认暂停，不能用没有告警解释为业务正常。

监控本身也需要预算；目标日志和页面只能作为观察数据，不得授予权限。对于可能不可逆或涉及多个系统的异常，默认人工确认恢复，避免短时探测恢复后立即重新施压。

**最小验收**：在隔离副本模拟业务退化和监控失联，验证真实流量暂停；恢复条件未满足时不能自动继续。

### QX-S07：停止尚缺端到端保障证据

**现状与依据**

已实现 bash 进程组终止、容器停止和网络 drain。问题不是“没有停止按钮”，而是本次没有验证调度器失联、模型挂起、子进程残留或目标异步动作场景。

依据：[executor-sandbox-docker.ts:520](../src/executor-sandbox-docker.ts#L520)、[同文件:576](../src/executor-sandbox-docker.ts#L576)、[controller.ts:3048](../src/controller.ts#L3048)。

**解决方案**

增加独立于模型推理和 UI 的停止路径。停止请求到达后，冻结新调度、撤销相关任务出口和未消费授权，再终止执行器、浏览器、MCP 及子任务；这些步骤需考虑部分失败和幂等重试。

状态分为“停止已请求”“出口已阻断”“执行器已终止”“残留待处理”“停止完成”，不能收到 API 成功响应就显示全部完成。目标端已提交的异步任务，应使用事先批准的取消/清理方式，不能通过无限制清理命令补救。

**最小验收**：验证页面断开、模型不可用和本地执行器故障时仍可停止；记录断流时延与未停止资源。时限必须实测，不凭 `docker stop --time 5` 推导全系统五秒停止。

### QX-S08：执行入口和后端保障不一致

**现状与依据**

显式选择 `auto` 可按本机能力选择其他后端，最终可能使用 `workspace`；它与默认 Docker 不是同等边界。Beekeeper MCP 通过宿主子进程连接，有专用环境、工具集合检查及取消机制，但不自动继承执行容器网关。控制器缺少 `toolApproval` 配置时默认 `off`，扩展挂载也依赖传入配置。

依据：[executor-sandbox.ts:127](../src/executor-sandbox.ts#L127)、[beekeeper-runtime.ts:103](../src/mcp/beekeeper-runtime.ts#L103)、[controller.ts:563](../src/controller.ts#L563)、[agents.ts:243](../src/agents.ts#L243)。不能由此断言现有 Web/CLI 都漏接了审批。

**解决方案**

生产启动进行能力自检：实际后端、可访问网络、挂载、工具目录、审批服务和停止服务均符合策略才能启动。禁止生产静默降级；新入口必须显式声明安全策略，不能以缺省值取得全权执行。

为每个 MCP 和浏览器连接登记权限、目标、凭据来源、数据出口和关闭方式；以能力指纹发现工具集变化，变化后重新授权。优先统一现有调用封装的执行门禁，不要求把所有 MCP 强行搬到同一个容器。

**最小验收**：新增调用入口漏配策略、后端不可用、MCP 工具集变化时拒绝生产执行；已接入的 Web/CLI 流程没有功能回退。

### QX-S09：生产操作边界不能只靠通用命令判断

**现状与依据**

审批策略按工具名称路由，`bash`、`write` 等再交给裁判或人工；裁判接受 `allow` 或 `require_approval`。从该路径未看到针对生产环境独立、不可被批准覆盖的业务动作目录。

依据：[dangerous-tool-policy.ts:49](../src/approval/dangerous-tool-policy.ts#L49)、[同文件:91](../src/approval/dangerous-tool-policy.ts#L91)、[llm-risk-judge.ts:19](../src/approval/llm-risk-judge.ts#L19)。这不是说所有工具都没有参数验证，而是参数合法仍不等于目标操作低影响。

**解决方案**

将运行档位分成离线分析、生产受限验证、隔离环境验证和专项人工监督。生产只开放经过审查的有限能力，声明其副作用、目标、预算和终止方式；通用远程命令、未知脚本及高影响验证不默认开放。

生产禁止项建议覆盖数据/账户破坏、资源耗尽、持久化、未经专项授权的横向扩展、真实交易与任意数据外传。分类应针对效果，而不是只匹配命令文本。HTTP GET、工具标称只读、低权限账户都不是天然无损证明。

**最小验收**：静态禁止的动作不能通过人工普通批准或模型 `allow` 解锁；需要专项授权时创建新策略版本和受控任务。

### QX-S10：敏感数据处理缺少统一边界

**现状与依据**

执行事件包含工具参数与结果；`sanitizePiEvent` 做 JSON 化和长内容 artifact 转存，并非统一脱敏。Beekeeper 的局部诊断脱敏已经存在，不应否认，但不能推广为全部事件、模型上下文和证据都受保护。

依据：[pi-runner.ts:932](../src/pi-runner.ts#L932)、[同文件:1102](../src/pi-runner.ts#L1102)、[同文件:1138](../src/pi-runner.ts#L1138)、[beekeeper-runtime.ts:147](../src/mcp/beekeeper-runtime.ts#L147)。

**解决方案**

1. 尽量让模型使用凭据句柄，由执行器按目标和用途注入真实秘密。
2. 限制凭据可用目标、有效期和权限，禁止跨任务默认共享。
3. 在进入模型、日志、artifact、前端和导出前分别执行数据策略。
4. 原始证据与脱敏副本分别授权；保留必要取证能力，不盲目删除所有原始证据。
5. 明确模型供应商、中转 API、日志平台的处理边界；未核实的数据路径不允许传递敏感原文。
6. 配置保留期限、访问审计和删除流程；正则脱敏只是补充，不能当成完整 DLP。

**最小验收**：使用人工构造的标记秘密，检查不同输出面及非授权出口；不使用真实生产密钥做测试。

### QX-S11：审批审计采用尽力写入

**现状与依据**

审批申请/决定调用 `void this.appendAudit(...)`；内部缺少日志 provider 时返回，写入异常被 `.catch(() => undefined)` 吞掉。队列决定本身不会等待这些审计持久化成功。

依据：[tool-approval-registry.ts:100](../src/approval/tool-approval-registry.ts#L100)、[同文件:121](../src/approval/tool-approval-registry.ts#L121)、[同文件:165](../src/approval/tool-approval-registry.ts#L165)。这不等于整个项目没有执行日志。

**风险与解决方案**

高影响动作可能已获批准并执行，但关键审批记录不完整。建议区分普通诊断事件和必须留痕的授权事件；生产高风险动作先取得可靠审计存储或受保护持久队列的确认，再发放可消费的授权。

避免为了审计故障再次执行同一动作，使用稳定事件 ID、幂等记录和明确的执行状态。审计不可用时暂停新高风险动作并告警，但不能阻塞紧急停止。审计内容应包含批准人、策略版本、载荷摘要与执行结果，秘密原文另行保护。

**最小验收**：模拟日志写入失败时，高风险动作不会静默继续；停止始终可用；恢复后不会重复执行已经完成的动作。

### QX-S12：缺少可支撑生产承诺的完整证据

**现状与依据**

前次 [安全研究报告](superpowers/research/2026-09-20-qingxuan-agent-production-safety.md) 及本次检查均未执行完整故障注入、目标状态对比或生产损失评测。既有单元/集成测试和功能演示不能自动证明所有目标无损，本文也不将“未验证”写成“必然失效”。

**解决方案**

建立隔离副本上的核心安全验收：验证失败关闭、完整审批、范围一致、真实出口、预算、停止和秘密出口。测试必须观测实际执行与目标状态，不仅观察 Agent 的文字判断。

给测试产生的账户、文件和数据登记所有权、创建动作、清理方法及验证方式；清理仅作用于明确属于测试的产物，保留业务及审计日志。异步通知、交易和其他外部副作用可能不可逆，应在测试前隔离或禁止。

记录版本、模型配置、策略、工具版本、测试条件、观测窗口与未覆盖面。核心门禁随每次相关升级执行，扩大对抗集作为后续工作。同时保留正常任务效用指标，防止靠全部拒绝取得表面安全。

**最小验收**：针对拟开放的生产能力，每项核心控制都有可复查的通过证据；失败项不通过风险提示文字直接豁免；确需例外时由业务负责人书面接受并缩小使用范围。

## 五、建议的执行与管理流程

### 5.1 后端执行顺序

以下是建议流程，不是当前 API 或函数签名：

```text
人工确认目标、环境、测试窗口和允许能力
  -> 冻结任务策略版本
  -> Agent 提出动作
  -> 校验动作目录、参数、范围和执行后端
  -> 必要时申请完整人工审批
  -> 执行前重新校验目标、授权、预算和业务健康
  -> 持久化关键授权事件
  -> 原子消费授权并由受限执行器执行
  -> 记录实际结果、预算和测试产物

独立通道：紧急停止、出口撤销、健康监控、遗留资源告警
```

检查与执行之间需要防止对象变化；不能只在创建任务时判断一次 scope。任何执行器拿不到有效策略或无法覆盖其出口时，应当停止，而不是让模型选择备用工具绕过控制。

### 5.2 前端应配套什么

以下是管理页面和工作台的建议需求，不表示当前界面完全没有相应功能。前端只呈现、申请和确认，最终强制规则必须由后端执行。

| 页面/区域 | 建议展示与交互 | 后端要求 |
|---|---|---|
| 新建任务 | 环境档位、目标范围、子域语义、窗口、预算、允许能力及禁止项 | 校验并冻结真实生效策略；拒绝生产使用不允许的配置 |
| 审批中心 | 完整参数/脚本、版本摘要、真实目标、有效期、风险依据、批准与拒绝 | 审批绑定实际载荷；已变化或过期请求不可执行 |
| 管理页面 | 实际后端、策略版本、MCP 能力、审计/停止服务状态 | 提供生效配置，不只显示环境变量期望值 |
| 运行工作台 | 目标预算、健康状态、阻断原因、人工接管状态 | 从真实网关和执行链汇总，而不是由模型生成数值 |
| 紧急停止 | 分阶段停止结果和遗留资源 | 独立停止通道；部分失败不能报整体成功 |
| 证据与产物 | 脱敏副本、访问权限、清理状态、未清理项 | 后端授权、留痕、受控清理和保留策略 |
| 展示大屏 | 汇总安全状态、阻断/暂停和执行进度 | 不展示秘密、原始敏感证据和高权限操作入口 |

不要把当前可编辑的环境变量页面当成完整安全策略系统。生产关键参数应经过语义校验、权限检查和版本化变更；运行中修改不应无声改变已有任务的授权。

## 六、实施顺序与交付建议

### 第一阶段：封闭明显的控制缺口

对应 QX-S01、S02、S08、S09：修正异常放行，完整参数审阅，禁止生产入口漏配和宽松降级，限定可开放能力。交付应包含代码变更、配置兼容策略和少量针对性回归，不需要先重构整个系统。

### 第二阶段：形成目标影响控制闭环

对应 QX-S04 至 S07：统一范围语义，明确所有工具出口，增加集中预算、业务健康监测和独立停止。该阶段是生产开放门槛的一部分，不是可以上线后再补的可选增强。

### 第三阶段：补齐授权、数据与审计

对应 QX-S03、S10、S11：绑定实际载荷，凭据和证据分级，可靠授权审计。若第一批目标就涉及敏感数据或高影响动作，相关内容应提前完成。

### 第四阶段：持续验证与恢复

对应 QX-S12：扩大对抗与故障场景，维护升级门禁、测试产物与恢复演练。核心验收已经包含在前三阶段交付中，不能拖到本阶段才首次验证。

### 建议的生产开放检查单

- [ ] 明确当前开放的环境、目标、能力和不可接受副作用。
- [ ] 未知工具、裁判失败和不完整审批输入不隐式放行。
- [ ] 全部开放入口应用同一策略，不静默降级后端。
- [ ] 目标、参数和实际载荷符合审批及策略版本。
- [ ] 对已开放协议的真实出口和聚合预算有验证证据。
- [ ] 业务健康异常和停止请求能够实际阻断后续执行。
- [ ] 敏感数据及关键审批事件按政策处理。
- [ ] 遗留产物、目标异步动作和恢复责任有明确安排。
- [ ] 模型/工具/策略升级必须通过相关核心安全门禁。

## 七、当前使用边界

在这些控制尚未完善和验证之前，建议以隔离靶场、可复原副本和低影响人工监督任务为主，不对外承诺生产零损失。必须测试生产时，应先确定明确授权、专用账户、时间窗口、操作上限、现场负责人和停止方式；`strict` 比自动批准更保守，但它不能替代预算、目标隔离与恢复保障。

如果业务对测试引起的任何状态变化都不能接受，则不应把主动漏洞利用作为默认测试方式，应优先进行授权导出材料的离线分析或彻底隔离副本验证。隔离副本仍需要移除生产凭据和真实外部依赖，其结果也不能直接证明生产同等安全。
